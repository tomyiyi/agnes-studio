## 第 4 轮（2026-10-01）：hssh 链中 heredoc 失效

- **现象**：经 `~/workspace/bin/hssh omarchy '... python3 - << "PYEOF" ... PYEOF'` 下发多行 python 补丁脚本，远端报 `/bin/bash: -c: line 6: syntax error near unexpected token '('`——bash 把 python 代码当 shell 解析，heredoc 未生效。
- **根因**：heredoc 操作符写在 hssh 单引号包裹的远程命令串里，经 hssh→ssh→远端 `bash -c` 多层转义后，`<< "PYEOF"` 重定向语义丢失（此前 `cat >> file << "EOF"` 能用是因为 heredoc 紧跟本地命令、本轮是嵌在引号内传参，两种形态不等价）。
- **定位**：对比成功/失败两条命令的形态差异确认；远端报错行号（line 6 = python 元组行）证明 python 源码进了 shell 解析器。
- **解法**：本地 `write` 工具写补丁脚本文件 → `scp -P 2223` 经主隧道（garbage.vicp.net:2223）送到 omarchy `/tmp` → `hssh` 单行执行。已验证 OK，后续跨机多行脚本统一走此通道，不再用引号内嵌 heredoc。

### 坑 2（工具链）：`pkill -f` 自杀——pattern 匹配到执行它的 ssh 会话自身

- **现象**：`hssh omarchy 'pkill -f "studio_server.py 18099"; sleep 2; ...'` 返回空输出 + exit 255，后续命令全没执行。
- **根因**：`pkill -f` 匹配完整命令行；hssh 传到远端的 `bash -c '...pkill -f "studio_server.py 18099"...'` 命令串本身就含有该模式串，pkill 先杀掉了执行它的 shell（ssh 会话），exit 255。
- **定位**：exit 255 + 零输出是典型自杀特征；`ss -ltn` 复查确认旧进程实际已被杀掉（pkill 在自杀前先命中了目标，属运气）。
- **解法**：bracket trick——`pkill -f "[s]tudio_server.py 18099"`（正则 `[s]` 匹配目标的 `s`，但字面 `[s]tudio...` 不会自我匹配）。已验证 OK。
- **搜索**：GitHub：ikalus1988/misakanet commit e157afd6411d37c36c5576a347645e1075eb6936（同类踩坑实录，含复现与 bracket trick）；全网：timmo001/dotfiles safe-process-signals SKILL（https://github.com/timmo001/dotfiles/blob/HEAD/agents/.agents/skills/safe-process-signals/SKILL.md）。结论：公认解法即 bracket trick / 按 PID 杀，本轮采用前者。

## 第 9 轮（2026-10-01）：`pkill -f` 自匹配杀死自己的 SSH 会话（exit 255 零输出）

- **现象**：验证完临时实例（:18099）后执行清理命令 `rm ... && pkill -f "studio_server.py 18099" && ...`，SSH 会话直接断开：exit code **255**、无任何 stdout/stderr、pkill 之后的所有命令（`ss` 校验、`git status`）未执行。
- **根因**：`pkill -f` 按**完整命令行**匹配；远端执行形态是 `bash -c "<整个命令串>"`，其 argv 本身逐字包含 `studio_server.py 18099`——pkill 先匹配到承载它的 shell，把自己杀了，SSH 通道随之死亡。表现极像网络/ssh flaky（255 + 零输出），实则是进程自杀。
- **定位**：255 + 零输出是典型指纹；`rm` 产物实际已删除（pkill 前执行）交叉印证"pkill 处断裂"；改用 `pkill -f "studio_server[.]py 18099"` 重试后 18099 成功停止、会话存活，反向证实。
- **解法**：括号技法 `pkill -f "studio_server[.]py 18099"`——pattern 里的 `[.]` 是 ERE 字符类（匹配字面 `.`），而 wrapper 命令行里是字面 `[.]` 三个字符，ERE 要求的位置是 `.` 而实际字符是 `[`，自匹配消除。更稳妥的通用方案：`pkill -x <进程名>`（只匹配 argv0，天然防自杀）；或 `pgrep -f '^python3 <脚本>'` 锚定解释器开头（wrapper 命令行以 `bash -c` 开头，锚定即排除）。注意括号技法有局限：若命令串后半段还逐字出现真实路径（不带括号），仍可能自杀——复合长命令优先用 `pkill -x`。
- **搜索**：GitHub——termio-sh/termio commit feb228c（"unanchored `pkill -f` kills its own ssh wrapper" https://github.com/termio-sh/termio/commit/feb228c808826af47a213afae2a2a800b54b70f4 ）；joeblew999/utm-dev-cli commit eab2ebe（exit 255 后改用 `pkill ` https://github.com/joeblew999/utm-dev-cli/commit/eab2ebeaa91dc412a840b6c7cc56306fe9218a49 ）；leyten/shard PR #27（self-match-proof `safe_kill` helper + 6 个测试 https://github.com/leyten/shard/pull/27 ）；hassancs91/content-factory-starter（bracket trick 局限性说明 https://github.com/hassancs91/content-factory-starter/blob/HEAD/content-factory/memory/lesson_pkill_matches_the_remote_wrapper.md ）。全网（中文）——bozhang1214/selfevolvingknowledgebase commit 550dbe89（"pkill -f 误杀 ssh shell 自身；部署在停服务取快照阶段被杀→生产 backend 留在 Exited 约 6 分钟" https://github.com/bozhang1214/selfevolvingknowledgebase/commit/550dbe893603e30b56d09d455abbbc8f1f1b5f3b ）。结论：公开已知的经典 footgun，本轮亲手踩实一遍；今后经 hssh 的 kill 命令一律用 `pkill -x` 或括号技法。

### 坑 B：Python urllib 不认 `no_proxy` 的 CIDR 写法（测试环境坑）

- **现象**：坑 A 的局域网回归测试（base_url=http://192.168.1.133:PORT/x）超时 10s 失败，而 127.0.0.1 用例正常。
- **根因**：omarchy 环境变量 `no_proxy=localhost,127.0.0.1,192.168.1.0/24,*.local`、`http_proxy=http://192.168.1.164:7897`。Python `urllib.request.proxy_bypass_environment` 只做精确匹配/前导点域名后缀，**CIDR 条目被当作字面主机名，永远匹配不上**——于是发往 192.168.1.133 的请求被送进黑苹果的 clash 代理，代理无法回连而 hang 死。127.0.0.1 在 no_proxy 里是字面条目，故正常——表现极具迷惑性（"回环通、局域网不通"）。
- **定位**：`echo $no_proxy/$http_proxy` 确认环境；`urllib.request.getproxies()` / `proxy_bypass("192.168.1.133")` 行为复核。
- **解法**：测试内用 `patch.dict(os.environ)` 把字面局域网 IP 追加进 no_proxy（studio_server 与测试同进程，urlopen 实时读环境变量）。生产建议：no_proxy 里对 Python 进程避免 CIDR，写字面 IP/域名。
- **搜索**：GitHub——rob--w/proxy-from-env#42（对照表：`Python urllib` CIDR ❌，curl ✅/Go ✅ https://github.com/rob--w/proxy-from-env/issues/42 ）；redhat-developer/rhdh corporate-proxy.md（"IP Address blocks in CIDR notation will not work" https://github.com/redhat-developer/rhdh/blob/HEAD/docs/corporate-proxy.md ）；pasumao/dsh-plugin-dev-kb（"CIDR ranges do not work… copying those into NO_PROXY has no effect" https://github.com/pasumao/dsh-plugin-dev-kb/blob/HEAD/kb/site/en/guide/network-proxy.md ）。全网（中文）——3304711297/youshouldknow《本地代理环境的 NO_PROXY 白名单与程序库代理行为》（"真正的差异发生在程序库层" https://github.com/3304711297/youshouldknow/blob/HEAD/docs/软件技巧/本地代理环境的NO_PROXY白名单与程序库代理行为.md ）。结论：公开确认的跨语言实现差异，curl 支持 CIDR 而 Python urllib 不支持。

## 第 14 轮（2026-10-01）：一个真实坑（安全）

### 坑：`api_key or def_key` 的"善意"重解析让路由层修复形同虚设（SSRF 密钥外泄向量 ×2）

- **现象**：对抗式审查发现两条服务端密钥外泄向量：(1) `resolve_chat_credentials`——请求显式 `base_url` 指向攻击者监听器且不带 key 时，服务端自动回退注入真实 key；(2) `/api/generate-image` 的 `api_key = req key or local_cfg key` 无条件注入。临时实例 + 伪造监听器实测前，修复方案只改路由层返回 `None`。
- **根因**：下游两处"善意"重解析——`agnes_engine.call_agnes` 的 `key = api_key or def_key` 与 `gateway_failover.post_with_failover` 的 `api_key is None → load_credentials()`——会把路由层好不容易置空的 key **悄悄捡回来**，照样发往恶意地址。只修路由层=假修复。这是典型的"纵深防御缺口"：安全语义必须在每一层都显式表达，不能依赖上游"应该传了空"。
- **定位**：读 `call_agnes`（`key = api_key or def_key`）与 `post_with_failover`（`if api_key is None: resolver()`) 确认重解析；用伪造监听器做**修复前/后对照**：修复前监听器会收到 `Authorization: Bearer <真实48位key>`（第 12 轮同构漏洞已证实该原语），修复后两次攻击均为 `Authorization=<ABSENT>`。
- **解法**：引入三态语义——`""` = 调用方明确"无密钥"（不再回退、不发送 Authorization 头），`None` = 走默认解析（旧行为）。`call_agnes` 改为 `key = def_key if api_key is None else api_key`；`resolve_chat_credentials` 重写为"显式 key 优先；显式 base 与服务端默认网关精确一致才注服务端 key；否则 `""`"；image 路由同规则门禁并透传 `""`。7 个新测试锁定三态语义。
